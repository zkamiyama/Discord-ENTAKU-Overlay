# ADR-0015: 活発な応酬に対する任意の左右2分割

- 状態: 採用。描画・回帰試験後に配布する。
- 日付: 2026-11-09
- 対象: RC.10、発話判定、カメラ、OBS Overlay、Dock

## 入力と限界

Discordの発話START/STOPと在席情報だけを使う。音声、声量、文字起こし、感情分類は追加しない。「白熱」を意味として認識するのではなく、2人の発話量と応酬の頻度を撮影上の代理指標とする。笑い、環境音、開いたままのマイクでは誤検出し得る。

## 判定

既存の10秒間の発話区間を再利用する。各人が2秒以上話し、2人の合計が全発話量の85%以上、少ない側も2人の合計の30%以上であることを要求する。同時発話は各人に計上するが、重なり時間と会話の継続時間は実時間で別に求める。少なくとも片方が話す時間は5秒以上とする。

加えて、有効な発話の交代が3回以上、または同時発話が1.2秒以上あることを要求する。700ms未満の発話は交代数へ加算せず、250ms以下の無音による細切れは一つの発話として扱う。双方が直近3秒以内に発話していることを確認する。3人目の継続発話があれば分割候補から外す。

これらは調整可能な実装上の初期しきい値であり、研究で検証された感情判定精度を主張しない。

## 状態遷移

条件が2.5秒安定してからSPLITへ入る。通常の話し始め2.5秒、話し終わり5秒の判定は維持する。分割中に片方が話し終わった場合もSTOPから5秒待ち、再発話で待機を取り消す。3人目の継続発話は2.5秒で全景候補とする。発話の偏りなどで分割条件が崩れた場合も5秒確認する。分割を終了した後は10秒間、分割への再入場を抑制する。

手動撮影と自動OFFを優先する。通信断・机の再配置は安全なワイドへ戻す。左右の人物は席順で固定し、10秒発話量の順位が入れ替わっても反転しない。

## 描画と安全性

Three.jsの公式マルチビュー例、PerspectiveCamera、WebGLRenderTargetを確認した。既存の後処理が画面をクリアするため、各半面を独立した描画ターゲットへ出力して合成する。WebGLコンテキストとシーン・素材は共有し、各カメラは実際の8:9の画角で人物・名札が収まるよう計算する。単一の16:9画像を切り取る方式にはしない。

露出は一度測光して両面へ共有し、DoFの対象とアイコンの向きは半面ごとに設定する。人物の色保持、透明度、机の深度、ニアクリップ、司会席後方の禁止は維持する。どちらかの安全な構図を作れないときは分割せず通常の撮影を続ける。分割終了時には専用の描画資源を解放する。

判定は軽量でも、2視点の描画は幾何形状・影・後処理の負荷を増やす。OBS実GPUでの性能は別途確認する。

## 操作と検証

Dockのカメラ設定へ「応酬が続く2人を自動で左右分割」を追加する。初期値はOFF。判断理由と発話割合・交代数・重なりを確認できるようにする。

単体試験は相槌、交互発話、重なり、偏った発話、3人目、再発話、境界時刻、10秒窓、手動優先、再入場抑制を扱う。描画試験は両面の独立した表示、色と透明度、焦点、画角、通常表示への復帰を扱う。

参照: Three.js公式 manual の Multiple Canvases Multiple Scenes と Render Targets、Discord公式RPC仕様のSPEAKING_START/SPEAKING_STOP。実装は固定したThree.js r187を確認する。
