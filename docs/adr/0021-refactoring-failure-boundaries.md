# ADR 0021：接続・設定保存・描画の失敗を分離する

## 決定

監査のP1から、正常時の見た目と設定を維持できる単位で処理を抽出する。全体のフレームワーク変更や依存ライブラリの更新は同時に行わない。

RPCは任意の利用者と、参加者状態の整合性を担う必須リスナーを分ける。任意リスナーの例外は接続全体を終了させない。定期VC同期のタイムアウトは同じ接続で回数を制限して再試行し、権限や壊れた応答を再試行で隠さない。ブラウザ側は古いソケットのイベントを新接続へ適用しない。

設定保存はHTTPの直列化と冪等性を維持したまま、SettingsServiceへ分離する。完了した保存だけを逆順に取り消し、取り消しの一部が失敗しても残りを試す。AppEngine内の同期的な計画が失敗した場合は、その処理直前の設定・席・カメラを復元する。非同期書込中のDiscordイベントは復元対象に含めない。

背景は候補を別グループとして読み、完成するまで表示中のシーンを保持する。描画効果のターゲットは名前と所有者を対応付け、不要になったものを一度だけ解放する。例外が起きた描画効果の再試行は、毎フレームではなく500ms・2秒の待機と回数制限を設ける。

## Three.jsの既存機能

Three.js 0.187.0のRenderTarget、disposeの説明、インストール済みのSSRPass・BokehShader・UnrealBloomPassの実装を確認した。

- [RenderTarget](https://threejs.org/docs/pages/RenderTarget.html)のsetSizeとdisposeをそのまま使う。EffectTargetsはアプリがどのターゲットを所有するかを管理するだけで、GPUの確保処理を作り直さない。
- [リソース解放の説明](https://threejs.org/manual/en/how-to-dispose-of-objects.html)では、解放済みの資源を再利用すると再生成される場合がある。dispose後の参照があるだけでバグとは断定しない。
- 現在のSSRの初期化補正、DoFの鮮明な範囲と透過保持は、採用中のaddonに対応する公開スイッチがない。既存の補正をアダプターへ移し、想定したシェーダー文字列が一度だけ現れることを検査する。SSRPassのssrMaterial解放も、この境界で扱う。

既存のGLTFLoaderによる読み込みと、人物・unlit素材の露出除外、深度による遮蔽は維持する。

## 限界

単一ファイルの原子的置換と、複数ファイルの補償的な書き戻しは異なる。今回は後者をプロセス内の例外処理として実装し、電源断・強制終了時の完全な一括復旧や書込ジャーナルは追加しない。

描画の再試行はJavaScriptの例外として報告された失敗を対象とする。GPUエラーの全種類を検出する仕組みや、自動で品質を下げる制御ではない。実GPUのフレームレート改善も、計測せずに主張しない。

実装範囲と試験結果は[実施記録](../refactoring-progress-2026-11-10.md)に記載する。
