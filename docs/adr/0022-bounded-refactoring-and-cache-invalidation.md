# ADR 0022：境界を分離し、変更時にキャッシュを更新する

## 決定

サーバーのHTTP処理は状態参照、資産、コマンドのルートへ分ける。変更操作の直列化、requestIdの冪等性、revision競合、Host・Originの検査は維持する。コマンドの型と外側の入力検査を共通契約にし、画像・スタジオの詳細検証は既存のドメインへ残す。

AppEngineから参加者管理、机の配置、撮影用の位置・サイズ情報を分離する。撮影用キャッシュは席・在席・画像・設定の変更で無効化し、発話だけの更新では再計算しない。発話統計は同じ時刻の結果を共用し、再発話や集計期間変更が同じ時刻に起きても無効化する。結果のコピーを返し、呼び出し側の変更をキャッシュへ持ち込まない。

撮影判断には型付きphaseを追加する。理由コードは従来の診断表示として残し、Dockは文字列末尾を解析して終了確認を判定しない。内部の撮影判断の順番・期限・安全条件は変えない。

## Three.jsの既存機能

[LightShadow](https://threejs.org/docs/pages/LightShadow.html)のautoUpdateとneedsUpdateを使い、世界座標の影を必要なときだけ作り直す。ライトの選択、影の境界、SSR対象の一覧もシーンの変更を基準に更新する。反射の有効化や机の伸長は更新に含み、カメラだけの移動は含めない。測光と影の更新キーを分け、机の伸長で露出の初期測光を毎フレーム繰り返さない。

[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)による取込検証は維持する。通常の素材は追加のWebGLRendererなしで解析する。KHR_texture_basisuを含む素材ではKTX2LoaderのGPU対応形式検出が必要なので、その場合だけ一時Rendererで検証し直す。素材の解釈を独自ローダーへ置き換えない。

シーン破棄にはThree.js標準のLight.disposeも使う。描画計測を繰り返した際、旧ライトのshadow mapが残ることを確認したため、ジオメトリ・テクスチャ・マテリアルに加え、ライトの影資源も所有するシーンと一緒に解放する。

## Dockとビルド

数値入力とスライダーは状態適用時に同期する。150msごとの全入力同期とMutationObserverによる全走査は外し、画像編集・診断・設定反映の各処理から明示的に同期する。カウントダウンと一覧更新のタイマーは非表示中に止め、診断と露出表示は一つの取得を共用する。

HTMLとCSSはビルド時に展開する。元の文字列とカスケード順が一致することを検証し、実行時のテンプレート処理や追加HTTP通信を増やさない。新しいUIフレームワークは導入しない。

## テストと配布

[Playwrightのsharding](https://playwright.dev/docs/test-sharding)を使い、全ブラウザ試験を独立した2ジョブへ分ける。各ジョブのテスト用サーバーは別環境にあるため、既存の固定テストポートを共有しない。ローカルではUIと描画の選択実行も可能にするが、全体試験は残す。

[gh release create](https://cli.github.com/manual/gh_release_create)による配布準備は、既存タグと対象コミットの一致を検査した後の手動下書きに限定する。実機確認や互換認証の配布条件を自動テストだけで満たしたとは扱わない。

## 維持する設計と残る検証

全量スナップショットの送信頻度は変えない。差分プロトコルは時計同期・再接続・描画補間の契約変更になるため、今回の責務分離とは別に扱う。AvatarStoreの画像容量検査も、外部ファイル変更を含む正確さを優先して維持する。

CPU計測は合成データによる制御処理の比較であり、OBSのフレームレートではない。描画計測はGPU名とsoftwareフラグを記録し、renderer.info.memoryは資源数として扱う。実GPUのメモリ使用バイト数、実スタジオの1080p60、実DiscordとOBSの長時間運転は別に確認する。

## 仕上げの補足

撮影の絶対期限はshot-transitionへ分離し、判定時にphaseを明示する。理由からphaseを得る関数は旧形式との互換用に限定する。旧実装との32,000ステップの比較で、追加phase以外の構図・理由・期限は一致した。

OverlayはAvatar、stage-frame、ProgramRendererへ分離する。画像編集の非同期ビルドはAvatarPreviewへ移し、画像の所有コピー、世代確認、終了時の破棄を一箇所で扱う。校正用プレビューでは二重のSSR・GTAO等を避け、本番の画質設定はそのままにする。

色・透過・深度とパス状態の復元は[描画パスの契約](../render-pipeline.md)に記載する。実機検証は利用者が担当し、Releaseの公開は実行しない。
