# ADR 0029: 公開ハッシュタグの受信と背景カード

日付: 2026-11-28 JST

状態: `feat/misskey-hashtag-cards`で実装。運用条件と測定値は[利用・調査記録](../misskey-hashtag-cards.md)を参照する。

## 課題

特定のMisskeyインスタンスにあるハッシュタグ付きノートを即時に受信し、ENTAKUの人物の背後へ浮かべたい。ノートの量や本文の長さは制御できず、削除・編集・荒らしにも対応する必要がある。通話の発話処理、カメラ、永続設定、録画へ外部ノートの生データを混ぜず、描画資源に上限を持たせる。

## 決定

### 入力・審査・表示を分ける

`MisskeyStream`がWebSocket、heartbeat、再接続、HTTP補完、captureを所有する。`MisskeyFeed`が正規化、採用判断、重複キャッシュ、待機列、表示期限を所有する。`MisskeyCards`は審査済みの短いカードだけを受け取り、Three.js資源を所有する。

`MisskeyState`は通話の`AppEngine`とは独立した購読で送る。録画、診断、プリセットへ本文を含めない。設定だけを既存SQLiteへ保存し、`SettingsService`の世代検査と直列処理を使う。保存失敗時は稼働中の設定と接続を変更しない。

初期設定は受信無効、otomad.site／NicoMiss、ローカル投稿者のみ、publicのみ、表示30件、待機60件、投稿者1件、45秒、180文字。homeは匿名で読める場合があってもpublicとは区別し、明示オプションとする。

### `hashtag` Streamingと有限の補完を使う

対象forkに存在する専用チャンネルを1つ購読する。openと購読ACKを区別し、WebSocket制御ping/pongで死活監視する。初回・再接続後のみ、最近2分を最大100件×3要求で補完する。429とRetry-Afterを扱い、再接続は1〜60秒のjitter付きバックオフとする。

採用されたノートだけでcursorを進めると、homeや対象外ノートの多いページで止まる。構造が有効な取得ノートをすべてcursorへ反映し、表示採用と取得済み範囲を分ける。遅れたHTTPやsocketイベントは接続世代を照合して無効化する。

表示と待機のノートだけをcaptureする。削除・編集通知では即時取り下げ、完全な再検査情報がない編集本文をそのまま反映しない。断線または過負荷で通知を追えなくなった場合もカードを消す。補完の上限に達したりHTTPが失敗したりした状態をUIに残し、完全な再送を保証しない。

### 機械的なフィルターを説明可能な範囲で採用する

MFMの構文処理には公式プロジェクトの`mfm-js 0.28.0`を追加する。独自の正規表現だけでMFM全体を解釈しない。得られた構文木から静的テキストだけを取り出し、画像・アニメーション・HTML・URLプレビューを評価しない。

全文の除外語判定、正規化全文のhash重複判定、反復検出、投稿者ごとの同時件数と採用間隔を組み合わせる。除外語は小さな独自辞書と利用者の追加語句とし、広い不適切語リストを丸ごと採用しない。文脈・意図を理解する判定ではないことをUIと文書で説明する。省略は審査の後に行い、切り落とす部分も検査対象とする。

### Three.js標準のSpriteを使う

リポジトリのThree.js 0.187.0について、公式の`Sprite`、`CanvasTexture`、CSS2D/3D、InstancedMeshの動作を確認した。30枚という規模では標準Spriteでカメラ追従と透明物体のソートを使う。カード1枚あたり512×256のCanvasTextureを割り当て、30スロットを再利用する。本文またはフォントの準備状態が変わったときだけ描き直す。

`SRGBColorSpace`、mipmapなし、`toneMapped=false`、`depthTest=true`、`depthWrite=false`を使用する。display layer 1に置き、影・反射・露出計算の対象外とする。カードは背景なので`renderOrder=-1`とし、通常の透明人物とSparkRendererより先に描く。複数人物をscene原点の1ノードへまとめるSparkでは、カードと同じrenderOrderの中心点ソートだけではstage移動時の前後関係を保てないためである。

配置は既存の机のカプセル形状を使い、10方向×3段の固定スロットとする。対向位置を交互に使い、カメラの近側を各ビューで抑制する。文字の幾何化、毎フレームのCanvas再描画、外部アバター画像の取得は行わない。期限にはreplay clockではなく実時間を使う。

## 比較した代替案

| 案 | 採用しなかった理由 |
|---|---|
| LTLを購読してタグを検査 | 専用hashtagが対象forkにある。無関係なローカル投稿を受け取る必要がない |
| 定期的な検索だけ | 取得の遅れと要求数が増える。接続前後の有限補完に限定する |
| 認証トークンの保存 | 今回の公開ノート購読には不要。限定公開を読む要件もない |
| 全履歴を永続保存 | 即時表示という目的に不要。削除追従と保管範囲が複雑になる |
| CSS2D/CSS3D | DOMの奥行きとWebGLの遮蔽を別途整合する必要がある。CSS2Dにはズーム条件もある |
| InstancedMesh＋アトラス | draw callは減らせるが、透明順序・個別フェード・文字更新範囲・アトラス管理が増える。最大30件では標準Spriteを先に測る |
| MSDFやTextGeometry | 多言語文字・絵文字のフォント資源とレイアウト管理を増やす。今回はCanvasのフォント処理で足りる |
| 大規模な不適切語辞書 | 一般語・引用・否定文の誤検出が多くなり、辞書の目的と配信用脅迫フィルターが一致しない |
| 外部LLMによる毎投稿の審査 | 遅延・料金・外部転送・依存先が増える。今回は機械的検査と管理操作を実装する |

## 検証と限界

単体・結合試験で寿命、上限、範囲、重複、補完、世代、heartbeat、429、削除、過負荷を確認する。ブラウザでは実際のカード、SPLIT、設定・除外・停止を確認する。描画実験は0件／30件、通常／SPLIT、1,000回の入れ替えを比較し、資源数と静止時の追加更新を記録する。

実接続では匿名購読ACKと約173秒の接続維持を確認したが、計測中に新着streamノートは観測していない。新着の実測遅延、実GPU、OBS/CEF、長時間の実配信は未検証である。30枚は実装上限であり、すべてのPCのフレームレートを保証しない。

接続先検査はHTTPSのホスト名などの構文境界に限る。DNS解決とproxy経路はBunへ委ね、解決先IPの固定はしない。書込みAPIは既存のsame-origin制限と設定世代検査を使い、Origin制限をローカルプロセスの認証とは扱わない。
