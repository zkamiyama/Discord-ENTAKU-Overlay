# ブラウザCIの描画と操作を分ける

本番の解像度や画質を変更せず、ソフトウェアGPU上の操作試験と画素試験を分離する。

## 切り分けた失敗

コミット74c4d2fのGitHub CIでは、Windows・Linuxのチェックは成功したが、ブラウザに3件の失敗が残った。画質操作試験は高解像度のソフトウェア描画で累積90秒を使い切り、増席ボタンのクリック待ちで終了した。Dockのテーマ試験は、使い終えたOverlayを描画し続けたまま画面を取得していた。

ポスト設定試験では、Dockに届いた撮影状態を確認した後、Overlayの初回描画を待たずに位置を読んでいた。変更前の値がnullで、変更後の正常な位置と比較して失敗した。

## 修正した試験の境界

画質操作、ポスト設定、席・テーマ、アバター編集の操作試験では、Overlayだけを640×360にする。実際のSSR・GTAO・SSGI・MSAA等を動かす点は変えない。150%の描画を選んだときは、実効倍率1.5とcanvasの960×540を検証する。

席に関する映像の確認が済んだら、そのOverlayを閉じてからDockの390・1024・1440pxと明暗テーマの画面を取得する。カメラ位置の比較は、Overlayが単独構図とEFFECTSを実際に描画し、位置属性が存在してから開始する。固定時間の待機だけで準備完了とは扱わない。

トレースは操作・DOM・通信を保持し、GPUと競合する連続スクリーンキャストだけを止める。明示的な画素取得と失敗時の画面保存は維持する。テストのタイムアウト延長、強制クリック、失敗試験の除外は行っていない。

画像編集の2つの通し試験にも同じ境界を適用する。編集を始める前にOverlayのEFFECTS描画を確認し、初期シェーダー生成と校正用プレビューの準備を無条件に重ねない。通常サイズのOverlay起動試験と、個別の画素回帰の解像度は変更しない。

## 検証範囲

修正後の画質操作試験は2コア制限で3回連続成功した。同じ制限で、席・テーマ、ポスト、画質の対象8件も成功した。GitHub側の最終成否は修正コミットのActions結果で確認する。

本番Overlayの既定値、既存の固定サイズの画素回帰、全51件の実行、実機用の1920×1080計測は維持する。ソフトウェアCIの成功を、OBS実機の1080p60の保証に置き換えない。
